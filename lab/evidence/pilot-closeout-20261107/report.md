# Standalone NAC pilot closeout — independent lab qualification

Status: in progress. This package extends, and does not replace, the frozen [rc9 baseline](../dhcp-qualification-rc9-20261107/README.md).

## Answers so far

- **Can a DHCP endpoint move corp → quarantine → corp without manual intervention?** **PASS on exact rc10 with a one-NIC Windows Server 2025 Desktop Experience endpoint.** Two complete cycles changed between `10.70.10.80/24` and `10.70.20.80/24` with ordinary DHCP, machine EAP-TLS, no manual renew, reconnect, or port bounce. The first three actions used the documented NAC API; the last Restore used the console. [Windows run and exact limits](runs/rc10-windows-one-nic/findings.md). The earlier one-NIC Linux rc9 UI baseline remains separately identifiable below.
- **Interruption times in this clean-instance run:** Quarantine CoA at `2026-11-07T07:59:25Z`: corp denial **1.436 s**, quarantine TCP success **75.925 s**. Restore at `08:01:45Z`: quarantine denial **2.201 s**, corp TCP success **116.100 s**. These values belong only to `rc9cleanui02`, with sequential fresh probes about once per second; they are not Windows timings. The 120 s DHCP lease and absence of a link-state change explain why new addressing waited for lease expiry. See [`probe-summary.json`](runs/rc9-clean-ui/probe-summary.json), [`endpoint-probe.jsonl`](runs/rc9-clean-ui/endpoint-probe.jsonl), and the bounded [endpoint](runs/rc9-clean-ui/endpoint.pcap0), [corp DHCP](runs/rc9-clean-ui/corp-dhcp.pcap0), and [quarantine DHCP](runs/rc9-clean-ui/quarantine-dhcp.pcap0) captures.
- **Does NAC accurately show connection and authorization?** **PASS for switch observation and its stated limit.** rc10's live UI and API reported eAPI `SUCCESS VLAN 10/20`, session replacement/ended state and CoA observation; the endpoint panel explicitly said `not_observed`. Packet and TCP evidence independently confirmed the Windows endpoint's address and access. The UI did not claim that switch ACK or VLAN alone proved application recovery. [Windows evidence](runs/rc10-windows-one-nic/findings.md).
- **Exact candidate passing the core, Windows and post-restart retests:** rc10 commit `b39649f138e126ed6689a53b590855061042e341`, independently rebuilt and installed `nacd` SHA-256 `35699eac162cc2a7315efced101bee3ec18ed87ab1cb108f06f9bb1a7b48195e`; FreeRADIUS 3.2.5; adapter SHA-256 `602c3fc5ff195c818bca6f5a15ca665b588077a07025315362cbb5331826c01b`; vEOS-lab 4.29.2F. The frozen rc9 commit `3e92642110f97d3f42a43652d33479e82cfbcc35` remains a separate baseline. The rc10 Account rotation also succeeded; a separately retained old-token test remains open.
- **rc10 measured Linux interruption times:** operator Quarantine: corp denial **1.964 s**, quarantine reachability **24.397 s**; operator Restore: quarantine denial **1.386 s**, corp reachability **110.933 s**. Rule-only corp→quarantine: corp denial **1.065 s**, quarantine reachability **72.114 s**; reverse rule-only change: quarantine denial **1.601 s**, corp reachability **79.464 s**. These belong only to the [rc10 core run](runs/rc10-core/probe-summary.json), not the rc9 or Windows runs.
- **Windows interruption times:** first Quarantine: corp denial **2.027 s**, quarantine reachability **33.418 s**; first Restore: quarantine denial **1.776 s**, corp reachability **61.423 s**. Second Quarantine: corp denial **1.728 s**, quarantine reachability **63.856 s**; UI Restore: quarantine denial **2.290 s**, corp reachability **34.433 s**. Each value is first observed fresh TCP, with about one-second probe resolution, from [one Windows run](runs/rc10-windows-one-nic/probe-summary.txt). The DHCP scope advertised a 120 s lease but no T1/T2 options; observed renewal was about 60 s, and T2 was not measured.
- **Pilot blockers:** no authorized physical Arista switch on an isolated port for unplug/reconnect. The rc10 Account page rotation succeeded and the old password returned HTTP 401; revocation of an independently retained pre-change token remains unverified because one was not retained before rotation. Physical MAB is outside this EAP-TLS pilot.

## TLS configuration actually tested

EOS 4.29.2F required importing the PEM files into its certificate stores before referencing their bare names in the SSL profile. Files were disposable and remain inside EVE; no private key is in this package.

```text
copy flash:nac-eapi.crt certificate:nac-eapi.crt
copy flash:nac-eapi.key sslkey:nac-eapi.key
management security
  ssl profile nac-eapi
    tls versions 1.2
    cipher-list ECDHE-RSA-AES256-GCM-SHA384:ECDHE-RSA-AES128-GCM-SHA256
    certificate nac-eapi.crt key nac-eapi.key
management api http-commands
  protocol https ssl profile nac-eapi
```

The disposable NAC guest used `SSL_CERT_FILE=/etc/nac/eapi-ca.pem` and `NAC_EAPI_INSECURE_SKIP_VERIFY=false`. Its trusted CA file SHA-256 was `38b2fa8012bd757fba31785038b9697e3ed585143d3eb96ab4ac71f1435718c4`. The switch's startup configuration was not changed by this TLS qualification.
