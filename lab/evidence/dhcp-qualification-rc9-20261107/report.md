# pilot-rc9 qualification, 7 November 2026

## Answers for the pilot

- **Can a DHCP endpoint move corp → quarantine → corp without manual intervention?** **Yes in the rc9 Linux lab, including the product console.** The same endpoint, certificate, port and one DHCP NIC changed VLAN and obtained usable addressing without manual renewal, reconnect or port bounce. The [console run](runs/candidate-3e92642-dhcp-rc9-ui-20261107/findings.md) exercised active-session Quarantine/Restore and rule-only v12 publish/reauthentication/v2 restoration. The [core](runs/candidate-3e92642-dhcp-rc9-core-20261107/findings.md) and [full-restart](runs/candidate-3e92642-dhcp-rc9-restart-20261107/findings.md) runs supplied continuous TCP timing evidence. Windows remains untested.
- **What interruption times were measured?** In the core active-session CoA run, corp denial began at **0.097 s**, but quarantine TCP first opened at **102.758 s**; on Restore, quarantine denial began at **0.419 s** and corp first opened at **66.460 s**. The full-restart rule-only sequence measured **1.322 s / 114.661 s** to denial/new access, and **1.742 s / 68.864 s** on restore. The override-precedence run measured **1.080 s / 117.099 s** to denial/new access and **1.156 s / 81.962 s** on individual Restore. Samples are fresh TCP connections at about 1 s cadence, measured from product API action timestamps. Natural DHCP address/route/DNS arrival closely tracked newly permitted access. In the [console run](runs/candidate-3e92642-dhcp-rc9-ui-20261107/findings.md), four CoA-to-new-lease delays were **88.9, 118.1, 61.5 and 119.5 s**; timestamped TCP checks confirm the outcomes but give only upper bounds because that run's continuous probe failed from endpoint ENOSPC. See [core](runs/candidate-3e92642-dhcp-rc9-core-20261107/analysis-coa-to-quarantine.json), [restart](runs/candidate-3e92642-dhcp-rc9-restart-20261107/analysis-to-quarantine.json) and [override](runs/candidate-3e92642-dhcp-rc9-override-20261107/analysis-quarantine.json) analyses. No established-connection result is claimed.
- **Does the product accurately show connection and authorization state?** **Yes for the tested switch-side facts.** The rc9 API and console showed certificate binding, matched rule, policy version, connected session, fresh eAPI SUCCESS and matching VLAN10/20. During eAPI loss the API showed `reachable=no`; after five minutes it showed `freshness=stale`, liveness `unknown`, while **364/364** fresh corp TCP connections still opened. Recovery restored fresh/connected state. Verified remained explicitly historical. [Observer](runs/candidate-3e92642-dhcp-rc9-observer-20261107/findings.md), [stale-state](runs/candidate-3e92642-dhcp-rc9-stale-20261107/findings.md) and [console](runs/candidate-3e92642-dhcp-rc9-ui-20261107/findings.md) evidence. The UI does not observe endpoint IP or application reachability; a CoA acknowledgement and observed VLAN alone do not establish those outcomes.
- **Which exact candidate passed?** The rc9 **clean install, API, packet and tested console workflow** passed at candidate commit `3e92642110f97d3f42a43652d33479e82cfbcc35`, nacd SHA-256 `d2d93e3ddc40a7eadcddfd3275f3d8a7aa5610ca07b43eb219bb9d59267a3749`. [Clean install](runs/candidate-3e92642-clean-rc9-20261107/findings.md) and [independent build/tests](runs/candidate-3e92642-dhcp-rc9-prep-20261107/findings.md) match the pin. OPUS later pushed a docs-only commit after rc9; it is a distinct PR head and was not the running candidate.
- **What blocks a network-administrator pilot?** Windows wired EAP-TLS/DHCP behavior, trusted production eAPI TLS configuration, and physical Arista unplug/MAB/fallback qualification. Clean rc9 installation, automatic service restart, account API password change and local host reset now pass. Clean-instance switch onboarding and interactive Account UI remain unverified. The console's Quarantine confirmation step was not captured, and the UI run's continuous probe was blocked by endpoint disk exhaustion; prior rc9 runs supply continuous access timings. Linux DHCP delays of roughly **62–120 s** need an operator expectation or supported endpoint/link strategy. This evidence does **not** certify a complete standalone pilot release.

## CoA and outage clarification

The active-session quarantine **request** at 01:43:45.021Z targeted the valid-certificate Et1 session. The switch returned CoA-ACK id 68, initiated a new EAP-TLS exchange, received RADIUS VLAN20, and showed SUCCESS VLAN20. Corp fresh TCP was denied by 0.097 s; quarantine TCP first opened only after 102.758 s when ordinary DHCP had moved the endpoint. The Restore request at 01:46:20.797Z got CoA-ACK id 185, new EAP-TLS/RADIUS VLAN10 and SUCCESS VLAN10; quarantine denied by 0.419 s, corp opened at 66.460 s. No operator endpoint reconnect or forced endpoint DHCP renewal occurred. Later rule publication and policy restoration required **explicit product Re-authenticate actions**, recorded in [core findings](runs/candidate-3e92642-dhcp-rc9-core-20261107/findings.md). Policy publication alone does not change an active switch session.

During [outage](runs/candidate-3e92642-dhcp-rc9-outage-20261107/findings.md), nacd stopped at 01:55:44.388Z while FreeRADIUS stayed up. Expected and actual: existing switch-authorized corp session kept forwarding (48/48 sampled TCP opens); after explicit endpoint supplicant teardown/Et1 clear, a **new** valid-certificate login received Access-Reject twice and had no corp access (27/27 blocks). This is fail-closed new authorization; the existing forwarding was switch-retained session state, **not cached NAC authorization**. After nacd recovered, the still-running supplicant retried without endpoint intervention, received VLAN10 at 01:58:13.430Z, and corp TCP reopened at 01:58:36.545Z. The immediate readiness check raced startup; settled checks passed.

One operator confusion remains: an observed VLAN can appear before the endpoint has usable addressing, although the CoA dialog warns about DHCP renewal. Rejected-endpoint diagnosis time was not measured. A human usability trial remains necessary. Product eAPI observation in this disposable lab uses relaxed switch TLS verification; a pilot requires a trusted switch certificate or the documented compatible SSL profile.
