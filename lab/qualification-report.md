The endpoint had only `ens3` plus loopback, no management bypass or default route. Two static probe source addresses, `10.70.10.50/24` and `10.70.20.50/24`, were on that one NIC so each newly opened TCP connection used the correct source for its VLAN. Neither EVE service bridge retained a host address during access probes. This static method needed no address renewal. A DHCP deployment must renew after VLAN changes; an endpoint agent reacting to EAPOL success/link change is preferable to bouncing the switch port, which interrupts every connection and can itself cause a new authentication. Port bounce can be a documented fallback if endpoint renewal is unavailable, but it must be logged separately from CoA and is not evidence of switch-initiated reauthentication.

## Outage and CoA clarification

The original handoff's outage probe cleared the switch session before testing, so it did not prove existing-session behavior. The [baseline clarification](clarifications.md) and exact replacement tested all phases. For the replacement, with only `nacd` down, an already authorized Et1 session retained VLAN10 and fresh corp TCP stayed OPEN. This was **switch session persistence**, not an authorization cache. The operator then explicitly stopped the supplicant and cleared Et1. The new attempt received Access-Reject at **11:38:26.676**, EAPOL Failure, and both TCP services were BLOCKED. Once `nacd` recovered, the supplicant automatically retried without another operator reconnect/reauth; Access-Accept VLAN10 at **11:38:58.721** preceded corp TCP OPEN after 30.2 seconds. The adapter has **no authorization-result cache** and fails closed when the decision service cannot answer. Expiry of an idle already authorized session was not measured. All three phases **PASS** against the agreed behavior; [packet timeline](runs/candidate-fe7c981-20261106/radius-timeline.txt), [action log](runs/candidate-fe7c981-20261106/actions.jsonl).

The original baseline CoA was a lab-script request, not a product action. Its first request id233 lacked NAS-Port-Id and got NAK/Error-Cause402. Corrected request id172 targeted identity `wired-endpoint-01`, MAC `00-50-00-00-02-00`, Et1, NAS `10.70.99.1`, VLAN10; ACK/200 was followed by switch-originated reauthentication and Access-Accept VLAN10. The operator manually changed the endpoint IP before post-change probes. [Full baseline record](clarifications.md).

The exact replacement **product CoA** had continuous endpoint probes. UI Quarantine request **id255** at **11:32:16.357** targeted the active Et1/MAC/NAS session with VLAN20; vEOS replied ACK/200 at .359 and initiated EAP/RADIUS; Access-Accept VLAN20 at .621. Fresh corp TCP changed OPEN→BLOCKED at 11:32:18.008; quarantine changed BLOCKED→OPEN at 11:32:37.927. UI Restore request **id78** at **11:33:11.773** got ACK/200, switch reauthentication and Access-Accept VLAN10; quarantine BLOCKED at 11:33:13.045 and corp OPEN at 11:33:33.060. **No manual endpoint reconnect, port bounce, switch clear or operator-triggered reauthentication occurred during this dedicated product CoA interval.** An already established corp socket held across the change timed out on its later HTTP request. The [continuous probe log](runs/candidate-fe7c981-20261106/probe-fe7coa.jsonl) and [RADIUS timeline](runs/candidate-fe7c981-20261106/radius-timeline.txt) preserve the order. Policy publication alone did not apply to the existing session; the product Re-authenticate action was explicit in the rule-change step.

## Qualification and repeatability

The [exact-candidate evidence matrix](runs/candidate-fe7c981-20261106/evidence-matrix.md) marks all twelve requested steps **PASS**, including the fresh-first invalid-CA and active-quarantine invalid-CA regressions. It marks MAB/fallback **BLOCKED**. The clean install used OPUS's documented bundle and installer; UI workflow registered the switch, bound the FreeRADIUS-validated issuer+serial+CN to the device record, previewed/published policy versions, Re-authenticated, Quarantined and Restored. MAC was compared with the registered device but never treated as sufficient identity. v2 rule required `identity.bound=true` **and** `mac.matches_device=true`; only the rule's segment changed in v3. Product decisions, rule/version and RADIUS VLAN attributes are correlated in the matrix; TCP probes decide enforcement.

The [runner](run_candidate.py) records lab actions, service-health checks, TCP probes, captures, outage and candidate-node restart. After the restart race was found, the current runner gained EOS readiness and service-health assertions before fresh probes; it passed Python syntax checking but has not been run end-to-end again. [Rerun instructions](rerun-candidate.md) and [sanitized settings](runs/candidate-fe7c981-20261106/configs.sanitized.txt) are included.

On the full candidate-node restart, an initial fresh probe was made while EOS was still booting and was **discarded as invalid enforcement evidence**. We waited for saved vEOS dot1x/VLAN configuration and independent HTTP200 service checks, then reran fresh unauthenticated, valid corp, persisted v3 quarantine and v2 restoration. The final restoration after restart used an **explicit operator `wpa_cli reauthenticate`**; a transient EAPOL failure preceded the eventual VLAN10/actual corp access. This manual step is disclosed and is separate from the dedicated product CoA proof. EOS startup config had earlier required `zerotouch cancel`, reapply and `write memory`; reboot then proved persistence. That requirement is in OPUS's later installation docs.
